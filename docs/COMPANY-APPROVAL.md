# Company approval and warehouse ownership

Registration from either client stores the person's requested company name in the account profile. The existing system administrator approval gate remains required. In **Manage users → Review/edit**, the administrator chooses the company name (with suggestions for existing companies), the system role, a separate role in that company, and Active status. Saving approval creates or reuses that company, creates a default main warehouse if needed, and grants the person membership plus a default warehouse assignment. The approving system administrator gains a persisted administrator membership in that company so they can operate its inventory.

The **Company and warehouse** panel displays real company names and codes, registration dates where known, warehouse selection, and expandable members/roles and company settings sections. Member controls set the company role, membership status and allowed warehouse IDs. System administrators can see all companies and explicitly open any one to gain its administrator membership. Company administrators can see only their own memberships and manage only their own companies. Staff cannot inspect other companies' members or warehouses. Creating a company never promotes a person to system administrator.

Two names are considered the same when Unicode compatibility normalization, letter case and repeated/leading/trailing whitespace differences are removed. `ePips`, `EPIPS` and ` ePips ` reuse the same company. A transactional `companyNames/{hash}` claim prevents races, and the backend checks older `meta/company` records that predate the registry. An existing company is never overwritten or taken over by a new registrant: it receives a pending staff membership until an administrator approves it. Renames enforce the same uniqueness rule. If several legacy companies already share a name, the operation reports a conflict; it does not merge or delete their inventory.

New companies receive a main warehouse immediately. In product intake, select a warehouse from the active company. The backend verifies that warehouse is accessible before saving the product's minimum stock settings and opening receipt. Successful intake selects that warehouse for the next page. A warehouse ID from a different company is rejected even if the actor administers both companies. Existing stale-form context checks and receipt approval gates remain in force. The company catalog is shared across that company's warehouses; quantities and reorder settings are warehouse-specific. Catalogs, stock, receipts and ledgers remain isolated between companies.

For accounts approved before this change, review the registered company name and save the Active account once to link it. This is deliberate: deployment does not change live account memberships automatically. Additional companies remain separate memberships; editing the primary company does not silently remove other memberships. Deactivating the global account blocks both clients even if some company memberships are still marked Active. Registration dates missing from legacy records display as "Not recorded" rather than an invented date.

The mobile adapter handles a reused company without overwriting its branding or creating duplicate draft warehouses. Pending requests preserve the previously selected company and show the existing modal's error area. The original mobile markup, styling and assets are unchanged. Deploy the backend and distribute the updated mobile build together for this onboarding behavior.

The company directory currently uses the backend's existing bounded-query policy: more than 1,000 metadata records produces an explicit error rather than a partial directory. Introduce a paginated directory before exceeding that limit. Normal operations continue to use the original IDs and the sequential codes added previously.
