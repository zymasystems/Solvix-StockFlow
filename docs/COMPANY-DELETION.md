# Delete a company and its employees

Only an active system administrator can use **Company and warehouse → Delete company and employee memberships**. Company administrators and staff cannot delete tenants. Opening the confirmation page does not change data. The POST requires antiforgery validation and the company's exact name.

The confirmation page lists affected members and distinguishes shared accounts, system administrators and employees eligible for optional account deletion. The checkbox **Also permanently delete Firebase sign-in accounts and profiles for employees who belong only to this company** is unchecked by default. Without it, employees retain their global sign-in account but lose this company membership. With it, eligible exclusive employees are removed from both Firebase Authentication and `users`. Shared accounts, the administrator running the operation, the administrator who started it, and system administrator profiles are always preserved.

Deletion first writes a persistent `companyDeletions/{id}` receipt. The backend blocks reads, writes, joins, approvals and company creation replays for that ID. A concurrent business transaction must retry against the deletion barrier. The store also blocks direct transactional writes to the company's subtree, including legacy-import writes. The mobile adapter clears cached company inventory on HTTP 410 without signing out a shared user.

For optional employee account deletion, a Firestore transaction rechecks the current profile role and the user's company indexes. It writes a `userDeletions/{uid}` barrier and marks the profile inactive before calling Firebase Authentication. All company membership creation paths read that barrier, preventing a concurrent join from making the account shared after it was selected for deletion. Profile role edits are blocked by the existing deletion marker. Firebase sign-in deletion is idempotent; the profile is removed only after that call succeeds.

Company membership indexes are removed for every recorded member. A retained user's primary company display name is changed to another remaining company, or cleared if it still referred to the deleted company and no other company remains. Other roles, status and personal fields are retained. Unapproved registrations that never became company members are not treated as employees of the company.

The complete `companies/{id}` subtree is then recursively deleted, including nested stock and descendants whose parent documents are missing. Firestore parent deletion alone would not remove those descendants. The company's name claim is released only after subtree cleanup succeeds. The global company/user code counters are retained, so deleted references are not recycled. A fresh request can later create a new company of the same name with a new ID/code; stale requests cannot resurrect the deleted ID.

Cleanup records per-member progress and can be resumed from the company panel if Firebase or Firestore fails. Company access remains blocked while paused. The employee-account deletion option is fixed once deletion starts. Completed deletion receipts and user deletion barriers remain as minimal administrative/retry records; company data and deleted account profiles are not restored by retrying.

No existing company or employee is deleted by deployment. Deletion only happens when an administrator submits the confirmation form. Distribute the updated mobile build to get its HTTP 410 cache handling. Tests use isolated Firestore emulator projects and a test identity directory, not live accounts.
